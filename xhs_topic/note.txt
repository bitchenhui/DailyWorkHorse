Agent 会写代码后

最近在看几套 Agent 工程化项目：能自动跑流程、加人工审批，也能把各种工具接起来。但真正落地时，最容易出问题的往往不是生成代码，而是谁来判断结果能不能信。

我把一个成熟项目拆成 agent 任务后，发现最难的不是写代码

01｜先把任务拆小
别一上来就说“帮我把整个项目做完”。更稳的做法是先选一个边界清楚的小任务，比如修一个 Bug、补一组测试、排查一次失败。输入、验收标准和回退方式先写清楚，Agent 才不容易在没边界的地方自由发挥。

02｜把结果变成证据
Agent 说“已经修好”不代表真的修好。我的习惯是要求它同时给出改动位置、复现步骤和验证结果，再自己跑一遍测试看差异。代码只是候选结果，能不能被证据支撑，才是决定是否合并的关键。

03｜审批点要卡在风险处
不是所有步骤都值得人工确认。整理日志、生成临时脚本可以少打断，但改核心逻辑、动依赖、碰配置和发布流程时，最好留审批门。否则看起来是自动化，实际只是把风险藏进了一条更长的命令链里。

04｜经验要给上下文
如果只把代码扔给 Agent，它不知道这个项目过去为什么踩坑。把设计约束、常见故障和团队约定整理成可检索的说明，比塞进一段超长提示词更有用。好的上下文不是越多越好，而是能把错误引到正确的地方。
